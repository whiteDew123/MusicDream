## 一、项目架构总览

八月搭建的 MusicDreamer 是一个**多端音乐平台**，包含三大产品形态：

```
MusicDreamer
├── musicBack/              ← Spring Boot 后端微服务（14 个模块）
│   ├── music_gateway       ← API 网关（端口 9000）+ JWT 全局鉴权
│   ├── Mod_login           ← 登录注册（端口 8001）
│   ├── Mod_songList        ← 歌单管理
│   ├── Mod_like            ← 收藏
│   ├── Mod_msg             ← 消息通知 + 评论
│   ├── Mod_setting         ← 个人设置
│   ├── Mod_recommend       ← 推荐 + 歌曲 + 歌手
│   ├── Mod_singer          ← 歌手管理
│   ├── Mod_capsule         ← 时空胶囊
│   ├── Mod_upload          ← 文件上传
│   ├── Mod_room            ← 播放室
│   ├── Mod_friend          ← 好友
│   ├── Mod_musicbox        ← 盲盒
│   └── Mod_recognize       ← 听歌识曲
│
├── playerFront/            ← Web 应用端（Vue3 + Stripe 风格，端口 5174）
├── adminFront/             ← Web 管理后台（Vue3 + Webflow 风格，端口 5173）
└── music-dreamer-mini/     ← 微信小程序（uni-app）
```

| Bug | 根因 | 修复 |
|---|---|---|
| 歌单删除 500 | Controller 先删主表 `song_list` 再删子表，外键约束拒绝 | 调换顺序：先 `list_music` → `likelist` → 最后 `song_list` |

| 修改密码 500 | 前端 api/setting.js 写的路径是 RESTful 风格 `/setting/{userId}/password`，后端实际是 `/setting/password`（从 X-User-Id 头拿 userId） | 对齐后端实际路径，去掉所有 URL 中的 userId 参数 |

## 三、技术难点与踩坑总结

### 3.1 Gateway 白名单的「双刃剑」

**问题**：白名单写了 `"/api/login/**"` 意味着整个 login 模块（包括需要登录的 `/current`、`/update`）都跳过了 Gateway JWT 解析。LoginController 自己解析 JWT 又因为 Authorization 头在白名单链路被清理而失败。

**教训**：AntPathMatcher 模式里 `/**` 是贪婪匹配，**永远不要把 `/api/xx/**` 整个模块放进白名单**。应该精确到具体方法路径，比如 `"/api/login"`（只放行 POST 登录）。

### 3.2 MyBatis-Plus 的原生 SQL 驼峰陷阱

**问题**：MyBatis-Plus 配置了 `map-underscore-to-camel-case: true`，但这个映射**只对实体自动生成的 SQL 生效**。`@Select`/`@Insert`/`@Delete` 注解里手写的原生 SQL 列名**不会自动转换**，必须和数据库一致（下划线格式）。

**教训**：写原生 SQL 时，列名一律用 `user_id` 而不是 `userId`，用 `list_id` 而不是 `listid`。

### 3.3 外键删除顺序

**问题**：先删主表 `song_list`，再删子表 `list_music`、`likelist` → MySQL 外键约束 `FOREIGN KEY (list_id) REFERENCES song_list(id)` 拒绝 → `DataIntegrityViolationException (23004)`。

**教训**：有外键关联的表，**删除顺序必须反过来** —— 先删子表，再删主表。

### 3.4 BOM 头导致 Java 编译失败

**问题**：PowerShell `Set-Content -Encoding UTF8` 写文件时自动加 BOM 头（`\ufeff`），Java 编译器不认这个不可见字符 → `非法字符: '\ufeff'`。

**教训**：Windows 环境下写 Java 源码文件，用 .NET `[System.IO.File]::WriteAllText()` + `UTF8Encoding($false)`（false = 不要 BOM）。

### 3.5 跨端两套 API 风格并存

| 模块 | 风格 | userId 传递 | 代表 |
|---|---|---|---|
| Mod_setting | URL 不带 userId | 从 Gateway 注入的 X-User-Id 头获取 | `PUT /setting/password` |
| Mod_songList | URL 不带 userId | 从 Gateway 注入的 X-User-Id 头获取 | `POST /songList` |
| Mod_like | 部分 URL 带 userId | 混用 | DELETE `/like/list/{listId}` |

**教训**：后端 API 设计应该统一风格。Gateway 已经能注入 X-User-Id，后端就不该再让前端传 userId 到 URL 里。

### 3.6 小程序特有的运行时限制

| 限制 | 解决方案 |
|---|---|
| 不支持 `URLSearchParams` | 手动用 `&key=value` 拼接查询字符串 |
| 不支持 `URL.createObjectURL` 预览图片 | 用 `uni.createObjectURL` 或 `tempFilePath` |
| 栈溢出（`seek(0)` 在 `onCanplay` 里触发递归） | 加防重入标志 `playing` |
| 域名校验 | 开发时勾选「不校验合法域名」，生产环境需要 HTTPS |

## 五、个人成长与反思

### 5.1 这个月学会了什么

1. **从单模块到微服务**：第一次接触 Gateway + Nacos + 多模块依赖管理，理解了服务注册发现、StripPrefix 路由、请求头透传。
2. **双设计系统切换**：Stripe 风格（应用端浅色 + 紫色强调）和 Webflow 风格（管理端白色 + 蓝色强调）两套设计规范，布局、颜色、间距完全不同。
3. **全链路调试思维**：一个 Bug 可能横跨 前端 → Vite Proxy → Gateway → Mod_xxx → Mapper → MySQL，能独立走完整条链路定位。
4. **生产级代码规范**：DTO/VO 分离、全局异常处理、密码 MD5 加密、唯一性校验、外键级联删除、未读数缓存。

### 5.2 最想改进的地方

1. **前端 API 风格不统一**：`api/auth.js` 有 `/login/current`，`api/setting.js` 有 `/setting/password`，两套接口风格（auth.js 用 LoginController，setting.js 用 SettingController），应该统一到一个模块。
2. **缺少单元测试**：所有 Bug 都是手动 curl 测出来的，没有写 `@Test` 覆盖关键业务路径（删除顺序、收藏重复、白名单匹配）。
3. **前端没有错误边界**：`onMounted` 里的 `catch {}` 吞掉了所有异常，用户只看到空页面，不知道是网络问题还是 401 还是服务端崩了。
4. **API 文档缺失**：没有用 SpringDoc/OpenAPI 自动生成 Swagger 文档，前端对接口路径的认知全靠看源码，很容易出现路径对不上的 Bug。

## 六、结语

八月从零搭建了一个横跨 Web 双端 + 微信小程序的音乐平台，踩了近 20 个 Bug，90% 是**接口契约不一致**导致的（前端写的路径 ≠ 后端实际的路径、前端认为的数据结构 ≠ 后端返回的结构）。最大的收获不是学会了某个具体框架，而是建立了**全链路调试思维** —— 一个 Bug 出来，从浏览器控制台到 Vite proxy 到 Gateway 到 Controller 到 Mapper 到 MySQL，能像剥洋葱一样一层层往里翻，直到找到根因。

> "代码不会说谎" —— 这句话在这个月的每一天都在被验证。
